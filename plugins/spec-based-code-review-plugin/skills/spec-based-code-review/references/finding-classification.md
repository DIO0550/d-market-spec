# 指摘分類ルール

コードレビューにおける指摘の分類基準。全エージェント共通で適用する。

---

## 分類一覧

| 分類 | 意味 | アクション | アイコン |
|------|------|-----------|---------|
| CRITICAL | 重大な問題 | 必ず修正 | 🔴 |
| WARNING | 要確認の潜在的問題 | 基本修正 | 🟡 |
| INFO | 参考情報 | 任意対応 | 🔵 |
| PROTECTED | 仕様が正当化する複雑性 | **現状維持推奨** | 🟢 |

---

## 根拠の種類

| 種類 | 説明 | spec文書 |
|------|------|---------|
| ルール根拠 | ユニバーサルな設計・パフォーマンス・テスト原則への違反（SRP, DIP, KISS, N+1等） | 不要 |
| 仕様根拠 | spec文書（implementation-plan, hearing-notes等）からの具体的引用 | 必要 |

ユニバーサルな原則はそれ自体が根拠となる。spec文書がある場合は追加の文脈として参考にし、PROTECTED判定等に活用する。

---

## CRITICAL: 重大な問題

### 定義

ユニバーサルな原則への重大な違反、または仕様に反する実装がある。

### 該当条件

**ルール根拠（spec不要）**:
- 循環依存の発生
- N+1問題
- メモリリーク（イベントリスナー未解除、クロージャによる参照保持等）
- セキュリティ上の問題

**仕様根拠（spec文書がある場合）**:
- implementation-plan の `[NEW]` ファイルが作成されていない
- implementation-plan の `[MODIFY]` 変更が適用されていない
- DoD の項目が満たされていない
- hearing-notes のスコープ内の機能が未実装
- テストTODOリストのシナリオがテストされていない

### 出力フォーマット

```markdown
### C-{NNN}: {タイトル}

- **次元**: {担当次元名}
- **対象**: `{ファイルパス}` L{行番号}
- **根拠**: {ルール根拠: 違反しているユニバーサル原則 / 仕様根拠: spec文書名 Section X: "引用"}
- **問題**: {問題の説明}
- **改善案**: {具体的な修正提案}
```

---

## WARNING: 要確認

### 定義

潜在的な問題があり確認が必要。ユニバーサル原則違反または仕様からの逸脱。

### 該当条件

**ルール根拠（spec不要）**:
- SRP/DIP 違反
- KISS 違反 — 不必要な抽象化・間接参照
- 1ファイル1関数の過剰分割、関数名によるファイル命名（凝集度の問題）。すり抜けバリアント: `{関数名.ts}/index.ts`（ディレクトリ名に拡張子）も同様
- パフォーマンス上の懸念（不要な再計算、並列化の機会等）

**仕様根拠（spec文書がある場合）**:
- hearing-notes のスコープ外の実装が含まれている
- exploration-report の既存パターンと異なる実装
- テストファイルの配置が規約と異なる
- DoD 項目が部分的にのみ満たされている

**ルール根拠で指摘した項目にspec文書上の意図的な根拠がある場合は、PROTECTED に昇格する。**

### 出力フォーマット

```markdown
### W-{NNN}: {タイトル}

- **次元**: {担当次元名}
- **対象**: `{ファイルパス}` L{行番号}
- **根拠**: {ルール根拠: 違反しているユニバーサル原則 / 仕様根拠: spec文書名 Section X: "引用"}
- **問題**: {問題の説明}
- **改善案**: {具体的な修正提案}
```

---

## INFO: 参考情報

### 定義

問題ではないが、将来の保守やリファクタリングの参考になる観察事項。

### 該当条件

- 既存パターンとは異なるが改善として妥当な実装
- 将来的な拡張ポイントの示唆
- ドキュメントの追加が有益な箇所

### 出力フォーマット

```markdown
### I-{NNN}: {タイトル}

- **対象**: `{ファイルパス}` L{行番号}
- **根拠**: {ルール根拠 or 仕様根拠}
- **観察**: {観察内容}
```

---

## PROTECTED: 仕様が正当化する複雑性

### 定義

表面的には冗長・複雑に見えるが、計画ドキュメントに明確な根拠があり、現状維持が推奨される実装。

**この分類がプラグインの最大の差別化ポイント。** ナイーブなレビューアーが「削減すべき」と指摘しそうなコードを、仕様根拠に基づいて保護する。

### 該当条件

- hearing-notes のエッジケース要件に対応するエラーハンドリング
- implementation-plan で明示的に選択された設計パターン
- テストTODOリストの各シナリオに対応する個別テストケース
- exploration-report の既存パターンに合わせた実装
- implementation-plan で可読性を優先して選択された構造
- 異なるドメイン概念を扱うコードが個別に実装されている（誤DRY防止）
- implementation-plan で意図的に SRP/DIP に反する設計が選択されている
- 計画で将来の拡張に備えて設けられた抽象化レイヤー（KISS例外）
- 計画で指定されたファイル分割方針に基づく構成（凝集度の例外）

### PROTECTED の前提条件

PROTECTED 判定はspec文書（計画ドキュメント）が存在する場合にのみ適用される。spec文書がない場合、意図的な設計判断を確認できないため、PROTECTED は使わず CRITICAL/WARNING/INFO のみで分類する。

### PROTECTED 優先ルール

あるエージェントが WARNING として指摘し、別のエージェントが PROTECTED として判定した場合、**PROTECTED が優先**する。仕様に根拠がある限り、保護を優先する。

### 出力フォーマット

```markdown
### P-{NNN}: {タイトル}

- **次元**: {担当次元名}
- **対象**: `{ファイルパス}` L{行番号}
- **表面的な印象**: {ナイーブなレビューアーが言いそうなこと}
- **仕様による正当化**: {spec文書名 Section X: "引用"}
- **結論**: 現状維持を推奨
```

## 指摘時の根拠確認ガイド

### ユニバーサル原則で判断可能（ルール根拠で指摘可）

以下はspec文書がなくてもルール根拠で指摘できる。ただしspec文書があり、意図的な設計判断が確認できた場合は PROTECTED に昇格する。

| 指摘 | ルール根拠 | specがある場合の確認 |
|------|----------|-------------------|
| 「SOLID原則に違反している」 | SRP/DIP原則 | 計画で意図的に選択された設計でないか確認 → 意図的なら PROTECTED |
| 「不必要に複雑」(KISS) | KISS原則 | 計画で将来の拡張に備えた構造でないか確認 → 意図的なら PROTECTED |
| 「このループは非効率です」 | パフォーマンス原則 | 計画で可読性優先の選択でないか確認 → 意図的なら PROTECTED |
| 「コンポーネントが大きすぎる」 | SRP原則 | 計画でこの粒度が決められた理由を確認 → 意図的なら PROTECTED |
| 「この抽象化は不要」 | KISS原則 | 計画でこの抽象レイヤーの目的を確認 → 意図的なら PROTECTED |
| 「コードが重複している」 | 誤DRY検出の判定フロー（変更理由テスト → ドメイン概念テスト）を通過した場合のみ INFO | specがあれば Step3（仕様確認テスト）も実施 |
| 「この関数は独立ファイルにすべき」 | ファイル凝集度の原則（概念的な凝集度を損なう場合は指摘しない） | 計画のファイル分割方針を確認 → 方針通りなら PROTECTED |

### spec文書がある場合のみ判断可能

以下はspec文書の記載と照合しないと判断できない。spec文書がない場合はこれらの指摘は出さない。

| 指摘 | 必要な仕様根拠 |
|------|--------------|
| 「このコードは冗長です」 | 仕様のどの要件が不要か？ |
| 「もっとシンプルにできます」 | シンプル化しても仕様を満たせるか？ |
| 「このテストは多すぎます」 | テストTODOリストのどの項目が不要か？ |
| 「この分岐は不要です」 | この分岐が処理するエッジケースは仕様で不要とされているか？ |
| 「別のライブラリを使うべき」 | exploration-report のライブラリ選定根拠は？ |
| 「メモ化すべきです」 | 再計算がパフォーマンス要件を満たさない根拠は？ |

**すべての指摘には「根拠」フィールドを必須で含める。** ルール根拠（ユニバーサル原則名）または仕様根拠（spec文書からの引用）のいずれかを記載する。

## PROTECTED対象外のアンチパターン

以下のアンチパターンは、spec文書の有無に関わらず常に指摘でき、かつ PROTECTED 判定の対象外とする（仕様が正当化する理由が原理的に存在し得ないため）。

| パターン | 分類 | 根拠 |
|---------|------|------|
| 循環依存 | CRITICAL | モジュール間の循環参照。常にアーキテクチャ上の問題 |
| セキュリティ上の問題 | CRITICAL | XSS, SQL Injection, 認証バイパス等 |
| 拡張子付きディレクトリ名（`{関数名.ts}/index.ts`） | WARNING | 「関数名によるファイル命名」のすり抜けバリアント。ディレクトリ名に拡張子を付ける正当な理由は存在しない |

**追加基準**: このリストは最小限に保つこと。新しいパターンを追加する際は、以下をすべて満たすこと:
1. プロジェクト・言語を問わず**常に**問題である
2. 仕様が正当化する理由が**原理的に存在し得ない**
3. ツール/エディタの誤操作で発生する（意図的に選択されることがない）

---

## 指摘番号の採番ルール

各エージェントは自分の出力内で独立に番号を振る:

- `C-001`, `C-002`, ... (CRITICAL)
- `W-001`, `W-002`, ... (WARNING)
- `I-001`, `I-002`, ... (INFO)
- `P-001`, `P-002`, ... (PROTECTED)

オーケストレーターが統合レポートを生成する際に、全エージェントの指摘を通し番号で再採番する。
