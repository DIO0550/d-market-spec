# 指摘分類ルール

仕様整合性レビューにおける指摘の分類基準。全エージェント共通で適用する。

---

## 分類一覧

| 分類 | 意味 | アクション | アイコン |
|------|------|-----------|---------|
| CRITICAL | 仕様違反 | 必ず修正 | 🔴 |
| WARNING | 要確認の潜在的問題 | 基本修正 | 🟡 |
| INFO | 参考情報 | 任意対応 | 🔵 |
| PROTECTED | 仕様が正当化する複雑性 | **現状維持推奨** | 🟢 |

---

## CRITICAL: 仕様違反

### 定義

implementation-plan / hearing-notes で明示的に要求された内容が実装されていない、または仕様に反する実装がある。

### 該当条件

- implementation-plan の `[NEW]` ファイルが作成されていない
- implementation-plan の `[MODIFY]` 変更が適用されていない
- DoD の項目が満たされていない
- hearing-notes のスコープ内の機能が未実装
- テストTODOリストのシナリオがテストされていない
- 循環依存の発生
- セキュリティ上の問題（仕様有無に関わらず常に CRITICAL）

### 出力フォーマット

```markdown
### C-{NNN}: {タイトル}

- **次元**: {担当次元名}
- **対象**: `{ファイルパス}` L{行番号}
- **仕様根拠**: {spec文書名 Section X: "引用"}
- **問題**: {問題の説明}
- **改善案**: {具体的な修正提案}
```

---

## WARNING: 要確認

### 定義

仕様違反ではないが、仕様の意図からの逸脱や潜在的な問題がある。

### 該当条件

- hearing-notes のスコープ外の実装が含まれている
- exploration-report の既存パターンと異なる実装
- テストファイルの配置が規約と異なる
- パフォーマンス上の懸念（ただし仕様でパフォーマンス要件がない場合は優先度低）
- DoD 項目が部分的にのみ満たされている
- 1ファイル1関数の過剰分割、関数名によるファイル命名（凝集度の問題）。すり抜けバリアント: `{関数名.ts}/index.ts`（ディレクトリ名に拡張子）も同様（仕様根拠不要）
- SRP/DIP 違反（計画ドキュメントに意図的な根拠がない場合）
- KISS 違反 — 仕様根拠のない不必要な抽象化・間接参照

### 出力フォーマット

```markdown
### W-{NNN}: {タイトル}

- **次元**: {担当次元名}
- **対象**: `{ファイルパス}` L{行番号}
- **仕様根拠**: {spec文書名 Section X: "引用"}
- **問題**: {問題の説明}
- **改善案**: {具体的な修正提案}
```

---

## INFO: 参考情報

### 定義

問題ではないが、将来の保守やリファクタリングの参考になる観察事項。

### 該当条件

- 既存パターンとは異なるが改善として妥当な実装
- 将来的な拡張ポイントの示唆
- ドキュメントの追加が有益な箇所

### 出力フォーマット

```markdown
### I-{NNN}: {タイトル}

- **対象**: `{ファイルパス}` L{行番号}
- **観察**: {観察内容}
```

---

## PROTECTED: 仕様が正当化する複雑性

### 定義

表面的には冗長・複雑に見えるが、計画ドキュメントに明確な根拠があり、現状維持が推奨される実装。

**この分類がプラグインの最大の差別化ポイント。** ナイーブなレビューアーが「削減すべき」と指摘しそうなコードを、仕様根拠に基づいて保護する。

### 該当条件

- hearing-notes のエッジケース要件に対応するエラーハンドリング
- implementation-plan で明示的に選択された設計パターン
- テストTODOリストの各シナリオに対応する個別テストケース
- exploration-report の既存パターンに合わせた実装
- implementation-plan で可読性を優先して選択された構造
- 異なるドメイン概念を扱うコードが個別に実装されている（誤DRY防止）
- implementation-plan で意図的に SRP/DIP に反する設計が選択されている
- 計画で将来の拡張に備えて設けられた抽象化レイヤー（KISS例外）
- 計画で指定されたファイル分割方針に基づく構成（凝集度の例外）

### PROTECTED 優先ルール

あるエージェントが WARNING として指摘し、別のエージェントが PROTECTED として判定した場合、**PROTECTED が優先**する。仕様に根拠がある限り、保護を優先する。

### 出力フォーマット

```markdown
### P-{NNN}: {タイトル}

- **次元**: {担当次元名}
- **対象**: `{ファイルパス}` L{行番号}
- **表面的な印象**: {ナイーブなレビューアーが言いそうなこと}
- **仕様による正当化**: {spec文書名 Section X: "引用"}
- **結論**: 現状維持を推奨
```

## 無効な指摘パターン

以下のような指摘は、仕様ドキュメントに根拠がない限り出してはならない。

| 無効な指摘 | 必要な仕様根拠 |
|-----------|--------------|
| 「このコードは冗長です」 | 仕様のどの要件が不要か？ |
| 「もっとシンプルにできます」 | シンプル化しても仕様を満たせるか？ |
| 「このテストは多すぎます」 | テストTODOリストのどの項目が不要か？ |
| 「この分岐は不要です」 | この分岐が処理するエッジケースは仕様で不要か？ |
| 「別のライブラリを使うべき」 | exploration-report のライブラリ選定根拠は？ |
| 「このループは非効率です」 | 計画でこの構造が選ばれた理由は？ |
| 「メモ化すべきです」 | 再計算がパフォーマンス要件を満たさない根拠は？ |
| 「コンポーネントが大きすぎる」 | implementation-plan でこの粒度が決められた理由は？ |
| 「この抽象化は不要」 | 計画でこの抽象レイヤーが設けられた目的は？ |
| 「このコードは重複しているので共通化すべき」 | 誤DRY検出の3ステップ判定（変更理由テスト → ドメイン概念テスト → 仕様確認テスト）を通過したか？ |
| 「DRY原則に反している」 | 2つのコードの概念的同一性を確認したか？表面的な類似だけで判断していないか？ |
| 「SOLID原則に違反している」 | implementation-plan / exploration-report でこの設計が意図的に選択された理由はないか？ |
| 「不必要に複雑」(KISS) | この複雑さが仕様要件に起因しないことを確認したか？次元5の意図的複雑性の保護に該当しないか？ |
| 「この関数は独立ファイルにすべき」 | 概念的な凝集度を損なわないか？1ファイル1関数の過剰分割になっていないか？ |

**すべての指摘には「仕様根拠」フィールドを必須で含める。** 引用できない指摘は PROTECTED に分類するか、除外する。

---

## 仕様根拠不要の例外

以下のアンチパターンは、仕様ドキュメントに言及がなくても指摘できる。これらはプロジェクト・言語・仕様を問わず常に問題となる普遍的なコード品質違反であり、PROTECTED 判定の対象外とする。

| パターン | 分類 | 根拠 |
|---------|------|------|
| 拡張子付きディレクトリ名（`{関数名.ts}/index.ts`） | WARNING | 「関数名によるファイル命名」のすり抜けバリアント。ディレクトリ名に拡張子を付ける正当な理由は存在しない |

**追加基準**: この例外リストは最小限に保つこと。新しいパターンを追加する際は、以下をすべて満たすこと:
1. プロジェクト・言語を問わず**常に**問題である
2. 仕様が正当化する理由が**原理的に存在し得ない**
3. ツール/エディタの誤操作で発生する（意図的に選択されることがない）

---

## 指摘番号の採番ルール

各エージェントは自分の出力内で独立に番号を振る:

- `C-001`, `C-002`, ... (CRITICAL)
- `W-001`, `W-002`, ... (WARNING)
- `I-001`, `I-002`, ... (INFO)
- `P-001`, `P-002`, ... (PROTECTED)

オーケストレーターが統合レポートを生成する際に、全エージェントの指摘を通し番号で再採番する。
