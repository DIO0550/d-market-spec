# レビュー次元定義

仕様整合性レビューの全次元定義。各エージェントが自分の担当次元を参照する。

---

## 次元一覧とエージェント割り当て

| # | 次元 | 担当エージェント | 核心の問い |
|---|------|----------------|-----------|
| 1 | 仕様充足性 | spec-alignment-reviewer | specに書かれた全項目が実装されているか？ |
| 2 | 意図整合性 | spec-alignment-reviewer | hearing-notesの「なぜ」とコードの「何」が一致しているか？ |
| 3 | 設計方針遵守 | design-reviewer | implementation-planのデータフロー・状態遷移・API設計に従っているか？ |
| 4 | 制約尊重 | spec-alignment-reviewer | exploration-reportの技術的制約・既存パターンを破っていないか？ |
| 5 | 意図的複雑性の保護 | **全エージェント共通** | 冗長に見えるコードにspec上の根拠があるか？ |
| 6 | テスト戦略整合性 | spec-alignment-reviewer | テスト方針と実際のテストが一致しているか？ |
| 7 | DoD検証 | spec-alignment-reviewer | Definition of Doneの全項目が実際に満たされているか？ |
| 8 | パフォーマンス | performance-reviewer | パフォーマンス上の問題はないか？ |
| 9 | アーキテクチャ整合性 | design-reviewer | 既存アーキテクチャとの整合性はあるか？ |

---

## 次元 1: 仕様充足性

**参照文書**: implementation-plan.md, tasks.md

### チェック項目

- [ ] `[NEW]` ファイルがすべて作成されているか
- [ ] `[MODIFY]` 変更がすべて適用されているか
- [ ] `[DELETE]` ファイルがすべて削除されているか
- [ ] tasks.md の完了状態（■）と実際のファイル状態が一致しているか
- [ ] 未完了タスク（□）が残っている場合、その理由が明確か

### 典型的な指摘

- CRITICAL: 「implementation-plan に記載された X が未実装」
- WARNING: 「tasks.md では完了(■)だが、実装が不完全」

---

## 次元 2: 意図整合性

**参照文書**: hearing-notes.md, implementation-plan.md

### チェック項目

- [ ] コードが hearing-notes の目的を実現しているか
- [ ] hearing-notes のスコープ外の実装が混ざっていないか
- [ ] 優先度の高い要件が確実に実装されているか
- [ ] hearing-notes の前提条件が変わっていないか

### 典型的な指摘

- CRITICAL: 「hearing-notes の目的 X に対応する実装が見当たらない」
- WARNING: 「hearing-notes でスコープ外とされた X が実装されている」

---

## 次元 3: 設計方針遵守

**参照文書**: implementation-plan.md, exploration-report.md

### チェック項目

- [ ] データフロー図と実装のデータの流れが一致しているか
- [ ] 状態遷移図と状態管理の実装が一致しているか
- [ ] API設計（エンドポイント・型・レスポンス）と実装が一致しているか
- [ ] コンポーネント分割方針に従っているか
- [ ] 命名規則が既存パターンと一致しているか

### 典型的な指摘

- CRITICAL: 「implementation-plan のデータフローでは A→B→C だが、実装では A→C に直結」
- WARNING: 「exploration-report の命名規則（camelCase）に対して snake_case を使用」

---

## 次元 4: 制約尊重

**参照文書**: exploration-report.md

### チェック項目

- [ ] 技術的制約（Section 3）が守られているか
- [ ] 既存パターン（Section 2）に従っているか
- [ ] 依存関係（Section 4）が壊れていないか
- [ ] テストインフラ規約（Section 5）に従っているか

### 典型的な指摘

- WARNING: 「exploration-report で特定された制約 X を無視」
- INFO: 「既存パターンとは異なるが、改善として妥当」

---

## 次元 5: 意図的複雑性の保護（全エージェント共通）

**参照文書**: 全計画ドキュメント

**この次元がプラグインの最大の差別化ポイント。**

### 判定フロー

```
コードが冗長/複雑に見える
  ↓
インテントマップを確認
  ↓
仕様に根拠がある → PROTECTED（現状維持推奨）
仕様に根拠がない → WARNING（簡素化を提案）
判断がつかない  → PROTECTED寄りに判定（誤って意図的コードを削るリスクを避ける）
```

### PROTECTED の典型パターン

| 表面的な印象 | 仕様根拠の例 |
|-------------|-------------|
| エラーハンドリングが冗長 | hearing-notes でエッジケース網羅が要求 |
| ループが分離されている | implementation-plan で可読性を優先 |
| テストケースが多い | テストTODOリストに個別シナリオが列挙 |
| 型定義が冗長 | exploration-report の既存パターンに合致 |
| 分岐が多い | hearing-notes のエッジケース一覧と対応 |
| 似たコードが繰り返されている | implementation-plan で意図的に個別処理 |

### WARNING の典型パターン（仕様根拠なし）

| 表面的な印象 | 仕様根拠の不在 |
|-------------|--------------|
| 未使用のコードが残っている | どの仕様項目にも対応しないデッドコード |
| 完全に同一のロジックが重複 | 仕様上分離する理由がない |
| コメントアウトされたコード | 仕様に記載のない実験的コード |

## 次元 6: テスト戦略整合性

**参照文書**: implementation-plan.md（テスト戦略セクション）, exploration-report.md（テストインフラセクション）

### チェック項目

- [ ] テスト方針（TDD / ポスト実装 / 手動）に従っているか
- [ ] テストTODOリストのシナリオがすべてテストされているか
- [ ] テストファイルの配置が既存規約に従っているか
- [ ] モック戦略が既存パターンと一致しているか
- [ ] テスト不要と判断された部分の根拠が妥当か

### 典型的な指摘

- CRITICAL: 「テストTODOリストの X シナリオがテストされていない」
- WARNING: 「テストファイルの配置が既存規約と異なる」
- PROTECTED: 「テストケースが多いが、テストTODOリストの全項目に対応している」

---

## 次元 7: DoD検証

**参照文書**: implementation-plan.md（Definition of Done セクション）

### チェック項目

- [ ] DoD の各項目を1つずつ確認
- [ ] 「コードが存在する」だけでなく「仕様通りに機能する」か
- [ ] DoD セクションが存在しない場合はスキップ

### 典型的な指摘

- CRITICAL: 「DoD 項目 X が満たされていない」
- WARNING: 「DoD 項目 X は部分的に満たされているが、仕様と異なる実装」

---

## 次元 8: パフォーマンス

**参照文書**: implementation-plan.md, exploration-report.md

### チェック項目

- [ ] 不要なループ・再計算、N+1問題
- [ ] メモリリーク・不要なオブジェクト保持
- [ ] 非同期処理の並列化機会
- [ ] レンダリング効率（フロントエンドの場合）
- [ ] バンドルサイズへの影響

### 典型的な指摘

- CRITICAL: 「N+1問題が発生している」
- WARNING: 「並列化可能な非同期処理が直列実行されている」
- PROTECTED: 「ループが分離されているが、implementation-plan で可読性を優先して決定」

---

## 次元 9: アーキテクチャ整合性

**参照文書**: implementation-plan.md, exploration-report.md

### チェック項目

- [ ] 既存の設計パターンに従っているか
- [ ] 状態管理の方針と一致しているか
- [ ] API設計の規約に従っているか
- [ ] 依存関係の方向が正しいか（循環依存の検出）

### 典型的な指摘

- CRITICAL: 「循環依存が発生している」
- WARNING: 「既存パターンと異なる状態管理アプローチ」
- PROTECTED: 「コンポーネント粒度が既存より細かいが、implementation-plan の方針に合致」
